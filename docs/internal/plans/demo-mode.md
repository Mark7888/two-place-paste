# Plan — Demo mode for the Android app

**Status:** proposed. Nothing has landed.

---

## 1. Why

Google Play review has to reach every part of an app, and asks for login
details to do it. TwoPlacePaste has no accounts: it needs a relay the user
runs, and there is no public one to point a reviewer at. Running a relay only
for review does not work either, because every update is reviewed again and a
review can take days.

A demo mode solves this inside the app. One tap starts a simulated relay and a
simulated second device in memory. The Sync, History, Store, Devices, Pairing
and Settings screens then work as they do in a real group, and nothing leaves
the phone.

The Play Console's *App content → App access* entry then needs instructions
only, with no username or password (§9).

## 2. Goals and non-goals

Goals:

- A reviewer can reach and use every screen with no server and no network.
- The demo runs the real client: real crypto, real wire frames, the real
  screens. Only the far end of the socket is simulated.
- Demo state never mixes with the device's real keys, history cache or store,
  and closing the demo leaves the app exactly as it was before.
- The entry point is low-key: a plain underlined text link at the bottom of
  the setup screen, not a full button.

Non-goals:

- Testing a real relay or the desktop app. The interop suite (`npm run
  interop`) already covers that.
- A demo on the desktop app. Play review is the only reason for this one.
- Keeping a demo across an app restart (§3, decision 3).

## 3. Decisions

1. **The simulated relay runs in process, behind `ClientOptions.socketFactory`.**
   The client already takes a `socketFactory`, `healthCheck` and
   `deviceStatus`, so it never has to know it is in a demo. The test fake relay
   (`src/core/protocol/__tests__/fakeRelay.ts`) becomes the demo's relay, and
   the tests keep using it.
2. **The demo has its own reserved relay address, `https://demo.invalid`.**
   `.invalid` is reserved by RFC 2606 and never resolves. The demo's socket
   factory refuses every other address, so a code from a real relay scanned
   during the demo cannot dial out by accident.
3. **Demo state lives in memory only.** The demo client gets an in-memory
   `SecureStore` and no entry cache. A restart (or Android killing the
   process) ends the demo and the app opens on the setup screen again. This
   keeps the real secure store untouched, and it means there is no leftover
   demo to clean up. The reviewer instructions say so (§9).
4. **The real client is set aside, not discarded.** Starting the demo
   disconnects the real (unpaired) client and keeps it. Closing the demo stops
   the simulated relay and devices and puts the real client back. The real
   device keypair is never regenerated by the demo.
5. **The demo is only offered from the setup screen.** A device already in a
   real group never sees it, which is the same rule joining follows. A
   reviewer's fresh install is always on the setup screen.
6. **"Leave the group" becomes "Close demo" in the demo.** Settings shows
   **Close demo** in the same place. Its dialog says the demo's data is
   discarded and the app goes back to the setup screen. There is nothing on a
   relay to warn about.
7. **The demo is always visible as a demo.** A thin banner over every tab
   reads "Demo — nothing leaves this phone". Play policy dislikes
   functionality a reviewer cannot see, and a user who found the link by
   accident must never mistake it for a real group.

## 4. The simulated relay (`src/core/demo/`)

Move `fakeRelay.ts` out of `__tests__` to `src/core/demo/relay.ts` so the app
bundle can import it. It has no React Native imports, so it stays in `core`.
Update the test imports (`client.test.ts`, `state.test.ts`) to the new path.

The fake relay handles 14 of the 25 request types the client sends today.
Add the rest, each following the SPEC section that defines it:

| Area | Requests to add | SPEC |
|---|---|---|
| Chunked entries | `ENTRY_UPLOAD_BEGIN`, `ENTRY_UPLOAD_CHUNK`, `ENTRY_UPLOAD_ABORT`, `ENTRY_FETCH_CHUNK` | §4.3, §6 |
| Store | `STORE_LIMITS`, `STORE_LIST`, `STORE_PUT`, `STORE_UPLOAD_BEGIN`, `STORE_FETCH_CHUNK`, `STORE_UPDATE_META`, `STORE_DELETE`, `STORE_LINKS` | §6b |

Plus the pushed events those flows need (store item added, updated and
deleted, sent to the other sockets in the group).

It stays a protocol fake, not a second server: no TTLs and no reclamation.
It does need to:

- cap memory: entry history to the last 20, total stored bytes to a few
  megabytes, with limits reported through `ENTRY_LIMITS` and `STORE_LIMITS`
  so the client's own size checks apply;
- expire offers and invitations by the clock it is given, so the pairing
  screen's countdown behaves;
- answer `healthCheck` with `true` and `deviceStatus` with `200` for devices
  that are in the group.

New tests (`src/core/demo/__tests__/relay.test.ts`) cover the added handlers
with the real `Client`: a chunked upload and fetch round trip, and each store
operation, including the events another socket receives.

## 5. The simulated devices (`src/core/demo/devices.ts`)

Two simulated devices, **Demo laptop** and **Demo tablet**, are real `Client`
instances with in-memory stores, joined to the demo group through the real
pairing flow when the demo starts. Two devices instead of one means the
reviewer can revoke one and still see sync work with the other.

On start, after pairing:

- the phone creates the group ("Demo group") through a creation token the
  relay hands out, like an operator's creation link;
- the laptop writes three history entries: a short text, a small PNG image
  generated in code (no binary asset in the repo), and a small text file;
- the store gets two items: a text snippet and the same image.

While the demo runs:

- every 90 seconds, and only while the app is in the foreground, the laptop
  copies a new line of text, so the reviewer sees an entry arrive;
- when the phone shows a pairing invitation, a third simulated device
  ("Demo phone") joins with it after 5 seconds, so the pairing screen
  completes. When the phone accepts or offers a code, it explains that a
  real device is needed, because there is nothing to scan.

Every timer is owned by one `DemoSession` object with a `stop()` that clears
all of them and closes every simulated client. Nothing runs after the demo
closes.

Tests (`src/core/demo/__tests__/devices.test.ts`) use an injected clock and
check: the seeded history and store, an entry from the timer, revoking the
laptop rekeys the group and the tablet keeps syncing, and `stop()` leaves no
timer running.

## 6. Session wiring (`src/app/`)

`sessionStore.ts` gains `startDemo()`, `closeDemo()` and a `demo: boolean`
in the snapshot (and in `SessionState` in `SessionContext.tsx`).

`startDemo()`:

1. disconnects the real client and keeps a reference to it;
2. builds the relay and the demo `DemoSession` (§5);
3. opens a demo client with the in-memory store, the demo socket factory and
   health stubs, the same handlers as the real one, and no entry cache;
4. clears `storeState`, transfers and notices, and emits.

`closeDemo()` reverses it: `DemoSession.stop()`, drop the demo client, clear
`storeState`, transfers and notices, put the real client back, and emit.

The quick settings tile keeps working in the demo, because it syncs through
the module's current client. The real clipboard is read and written, which is
what a reviewer would expect from a clipboard app; nothing leaves the phone.

A deep link or a scanned code from a real relay that arrives during the demo
is not attempted. The user is told "Close the demo first to join a real
group."

## 7. Screens

- **`ui.tsx`:** a `LinkButton`: underlined text in the accent colour, no
  background or border, a 44 dp touch target, and
  `accessibilityRole="button"`.
- **`SetupScreen.tsx`:** a `LinkButton` labelled "Try a demo" below the last
  card, at the bottom of the scroll view, with one muted line under it:
  "Simulated relay and devices. Nothing leaves this phone." No confirmation
  dialog.
- **`App.tsx`:** the "Demo — nothing leaves this phone" banner above the tabs
  while `session.demo` is true.
- **`SettingsScreen.tsx`:** in the demo, the "Leave the group" button becomes
  **Close demo** (same place and danger style), with the dialog "Close the
  demo? Its group, history and store are discarded and the app returns to its
  setup screen." The relay row shows "Demo (simulated)" instead of
  `demo.invalid`.
- **`PairingScreen.tsx`:** in the demo, the accept and offer options say that
  pairing a device by its code needs a real relay; showing an invitation works
  (§5).

## 8. Security review points

- No network in the demo: the socket factory refuses any address but
  `demo.invalid`, and the health stubs never call `fetch`. A test asserts
  that the demo makes no `fetch` call and dials no other address.
- The real keypair and secure store are never read or written by the demo.
  A test opens the real client, runs and closes a demo, and checks the stored
  state is unchanged byte for byte.
- No demo key, entry or store content goes to a log, the same as real state.
- The demo adds no new permission, and no new dependency.

## 9. Play Console and docs

**App access** in the Play Console: choose "All or some functionality is
restricted", and add one entry with no username or password:

> TwoPlacePaste syncs the clipboard through a server the user hosts, so
> there is no account or login. To review every feature without a server,
> open the app and tap **Try a demo** at the bottom of the first screen. It
> starts a simulated server and simulated devices inside the app, with no
> network access, and every tab then works. Settings → **Close demo** returns
> to the first screen. The demo is not kept if the app is closed: tap
> **Try a demo** again.

**Docs site:** a short "Try the demo" section in
`docs/site/src/content/docs/install/android.mdx` (what it is, what it does
not test, how to close it), and a line in `guides/settings.mdx` for
**Close demo**. Retake the setup screen screenshot, which now shows the link.

## 10. Order of work

One PR, all in `mobile/` and `docs/`; no wire, proto or server change.
Commits in this order:

1. Move the fake relay to `src/core/demo/relay.ts`, update test imports.
2. Add chunked entry and store handling to it, with tests.
3. Add `DemoSession` with the simulated devices and its tests.
4. Wire `startDemo` and `closeDemo` into the session store.
5. Screens: `LinkButton`, setup link, banner, Close demo, pairing notes.
6. Docs site section, screenshot, and this plan's status.

Checks before pushing: `npm test`, `npm run lint`, `npm run typecheck` in
`mobile/`, and `npm run build` in `docs/site/`. Then a manual run on a device
or emulator: start the demo, go through every tab, use the tile, close the
demo, and check the setup screen is back with the same device fingerprint.

## 11. Open questions

1. Should the demo also be reachable after a real group has been left, or
   only on a fresh install? (This plan: whenever the setup screen shows.)
2. Is 90 seconds the right interval for the laptop's new entry, or should it
   only send one when the phone uploads something?
3. Keep the demo across a restart after all? It would need a flag in the
   secure store and a separate demo state name. This plan says no (§3,
   decision 3).
